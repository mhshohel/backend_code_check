One shop, built three times

An order fulfillment and inventory platform: customers search and buy shoes, warehouse operators ship from two warehouses (WH-EAST, WH-WEST), administrators watch jobs and change prices. The same product is implemented with Express, Fastify and Next.js on top of one shared application layer, one PostgreSQL schema and one GraphQL contract. All three pass the same 14 acceptance scenarios.

Each page below is an animated walkthrough. Choose a scenario, press ▶ Play (or Step ▶), and watch the request travel from the user through the framework into the shared core, the database, the worker and back. Click any box to see what it does and where its code lives. The Try it tab gives the real commands for your machine.

How one request travels

StageWhat happensWhere
1. BrowserReact SPA (Express, Fastify, NestJS) or Next.js pages send GraphQL over HTTP with the ofl_session cookie and the x-ofl-csrf: 1 header; live order status uses graphql-ws.packages/web-spa, implementations/nextjs/app
2. FrameworkCorrelation id, security headers, CORS, rate limit, session, CSRF — expressed as middleware (Express), hooks in scopes (Fastify), middleware + guards + an exception filter (NestJS) or guards around route handlers (Next.js).implementations/*/api, nextjs/modules/server/http
3. GraphQLThin resolvers: check the viewer, parse input, call one operation, map the result to a typed union.packages/server-core/src/graphql
4. OperationOne transaction: business rows + outbox rows + pg_notify. Pure rules from @ofl/domain. Row locks in a fixed order prevent overselling.packages/server-core/src/features
5. WorkerClaims outbox jobs (SKIP LOCKED, 30 s lease), calls the payment gateway or Elasticsearch with idempotency keys, retries with backoff.packages/server-core/src/worker
6. Live updatePostgreSQL NOTIFY wakes every API process; the subscription re-reads the order and pushes it to the browser.packages/server-core/src/realtime
